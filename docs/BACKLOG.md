# BACKLOG — осознанно отложенное (не блокеры релиза)

Заведено по ревью 0.6.0. Ни один пункт не влияет на корректность — это рост,
архитектура и устранение мёртвого API. Не чинить впопыхах: каждый требует
своего мини-дизайна и теста.

## P3.3 — `bump_tokens` не уменьшается при архивации
Давление компакшна считается по счётчику токенов сессии; после выноса сообщений
в архив счётчик завышен → лишние саммари. Не потеря данных, но тихий перерасход.
Идея: `mark_archived` знает `session_id` строки → уменьшать счётчик сессии на
оценку токенов вынесенного текста. Нужен аккуратный тест на сходимость давления.

## P3.4 — `archive.search` + `include_archived` — мёртвый API
`archive.search` написан, но никуда не подключён; `include_archived` есть в
`session_messages`/`recent`, но recall-флаг «искать в холоде» не заведён.
Развилка: (A) подключить к `mem_recall(include_archived=true)` — тогда архивные
заглушки снова станут матчиться семантикой; (B) удалить как YAGNI, оставив
доступ к холоду только по id через `mem_expand`. Решить вместе с P4.8.

## P4.5 — `_dedupe_live_slots()` — полный скан на каждом открытии БД
Идемпотентная миграция выполняется при каждом `Store(...)`. При stdio это раз
за старт (терпимо); при росте стора — записать флаг в `um_meta`
(`slots_deduped=1`) и пропускать скан.

## P4.8 — вектора вытесненных/истёкших фактов остаются в `um_vectors`
Корректность не страдает (фильтр на чтении прячет истёкшее), но стор растёт.
Идея: при supersede/expire факта удалять его вектор из `um_vectors`/vec0
(история остаётся в теле, recall истёкшего всё равно через `include_expired`
идёт по тексту, не по вектору). Согласовать с P3.4.

## Прочее, подтверждённое как «по решению» (не чинить)
- Изоляция `owner=""` добровольная (legacy видит всё) — контракт, зафиксирован
  `test_legacy_migration`.
- Lazy-maintenance на read-path — осознанный компромисс для stdio; хост может
  дёргать `mem_doctor(mode=retention)` из cron.
- `as_of` = конец суток vs `valid_until` = начало суток — асимметрия
  задокументирована в README.
