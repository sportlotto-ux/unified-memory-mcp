# v0.5 PLAN — факт-лайфсайкл + temporal-граф (финал после обсуждения)

Скоуп v0.5 = пункты 0+1+2. Evidence (cite/compute) и conflict-detect → v0.6.
Публикация ✅ выполнено: origin публичен (`sportlotto-ux/unified-memory-mcp`), теги v0.6.0/v0.7.0.
Порядок: 0 → 1 → 2, TDD (красный тест → фикс), live MCP-check на каждом.
Цель: +~21 тест (→ ~130), версия 0.5.0. Аудит — после зелёных 0–2.

## Решённые развилки

- **Q1 — canonical-слот структурно, без env-флага.** Частичный уникальный индекс
  `UNIQUE(owner, category, name) WHERE valid_until = 0`: «два живых значения в
  слоте» невозможны на уровне БД, а не проверкой в Python. Граница навсегда:
  `mem_remember` = сырой лог (append-only, lossless), `mem_fact` = слот
  (одно живое значение + история). `UM_FACT_UPSERT` не вводим.
- **Q2 — отдельный `mem_update`.** Адресация по id ≠ слот-ключ; MCP-схема не
  выразит «либо id, либо category+name» → мутная рантайм-валидация. Сигнатуру
  `mem_fact` не трогаем.
- **Q3 — conflict-detect целиком в v0.6.** Keyword-эвристика даёт ложные
  срабатывания; при canonical-слоте supersede уже разрешает конфликт; API
  `conflict:{with_id}` почти наверняка поменяется с приходом LLM-судьи. Память —
  система доверия, шумный детект подрывает recall целиком.

## Согласованные детали (из ревью)

- **A. Sentinel `valid_until = 0` = живое.** Ловушка: `DEFAULT 0` + фильтр
  `valid_until < now` немедленно «истекает» весь стор. Живое = `valid_until = 0
  OR valid_until > now`. Колонка `REAL NOT NULL DEFAULT 0` (NULL-строки выпали бы
  из `WHERE valid_until = 0` и обошли partial-индекс).
- **B. `mem_forget` остаётся жёстким DELETE** (тест + GDPR/redaction escape
  hatch). Истечение — только через `mem_update(valid_until=...)`. Никакой смены
  семантики существующего тула.
- **C. Expire-then-insert атомарно** внутри `@_locked`; `IntegrityError` —
  backstop, не основной путь.
- **D. `mem_update` умеет reopen:** `valid_until=0` снимает истечение (без этого
  ошибочная инвалидация лечится только DELETE+re-add с потерей id).
- **E. `superseded_by` на `um_facts`** (цепочка как у саммари). Рёбрам — только
  `valid_until`; замена ребра = новое ребро, связь через существующий `fact_id`.
- **F. Порядок миграции:** сначала детерминированный dedupe-проход живых
  слотов, потом `CREATE UNIQUE INDEX` — иначе индекс упадёт на грязной БД.
  Dedupe lossless: старые помечаются superseded, не удаляются.

## 0. valid_until + update + invalidate (фундамент) — ✅ ГОТОВО (18 тестов + live MCP-check)
- Схема: `um_facts += valid_until REAL NOT NULL DEFAULT 0, superseded_by INTEGER
  NOT NULL DEFAULT 0`; `um_edges += valid_until REAL NOT NULL DEFAULT 0`.
- Миграция: ADD COLUMN guards → dedupe живых слотов (keeper = max(id)) →
  partial unique index через `_INDEXES` (после миграций).
- `mem_update(kind, id, body?, importance?, valid_until?, owner?)`:
  сперва valid_until in-place (0 = reopen), затем body/importance как новая
  версия (supersede-цепочка). Редактирование истёкшего без reopen — громкая
  ошибка.
- `mem_recall`/`mem_recent`: по дефолту прячут истёкшее; `include_expired=True`
  для аудита. `mem_expand(fact/edge)` отдаёт valid_until (+ superseded_by).
- Готовность: update не плодит дублей; истёкшее не в топе; чужой owner не
  правится; существующие БД (valid_until=0) живут как раньше.

## 1. temporal-граф (на плечах п.0) — ✅ ГОТОВО (5 тестов + live MCP-check)
- `mem_recall(..., as_of=ISO-date)`: граф-рука фильтрует рёбра по
  `valid_from <= as_of < valid_until` (0 = открыто). Закрывает
  mnemosyne `triple_query(as_of)`.
- `mem_update(kind=edge, valid_until=...)` = `triple_end` без отдельного тула.
- Готовность: срез графа на прошлую дату воспроизводим; `as_of` (ось
  валидности) и окно `mem_recent` (ось создания) не путаются.

## 2. canonical-семантика фактов (upsert-цепочка) — ✅ СДЕЛАНО В П.0
- `mem_fact`: то же тело → no-op (тот же id); новое тело → старое
  `valid_until=now, superseded_by=new`, новое живое; история lossless,
  recall отдаёт только живое.
- Готовность: дискордантная пара (чай: зелёный → чёрный) — в топе только новое;
  старое достаётся через `include_expired`; forced second live INSERT падает
  IntegrityError (структурный backstop).

## 3. Retention + архив — ✅ ГОТОВО (10 тестов), ядро: сообщения
Решено (i): RETENTION_DAYS = время в ГОРЯЧЕЙ (не срок жизни). Weekly: (а) горячее
старше N -> архив; (б) если размер > порога -> добить oldest. retention=0 -> только (б).
Автоудаления НЕТ (только ручной purge, lossless-холод). Архив вечен.
Цель: горячая БД не растёт бесконечно, но по умолчанию ничего не теряется.
Принцип: `mem_remember` (переписка/логи) — расходник; `mem_fact`/`um_summaries`/
граф — долговременное знание. Рёбра — только durable-знание, НЕ операционка
(деплой агент перечитает из кода; авто-вытягивания deploy-деталей в граф нет).

Решено:
- `UM_RETENTION_DAYS` = 0 (дефолт; копим вечно). README — явно и заметно.
- `>0` → автоудаление раз в неделю, но только после выноса в архив.
- Порог размера горячей БД (`UM_ARCHIVE_SIZE_MB`, дефолт 1024) → вынос старейшего.
- Вариант (а): сырой текст `um_messages` вытесняется первым; в горячей БД
  остаётся заглушка `[archived: <file>#<id>]` + ВЕКТОР. Семантический recall
  старое находит, `mem_expand` тянет текст из архива.
- Порядок выноса по `created_at`: (1) `um_messages` текст, (2) истёкшие
  факты/рёбра, (3) `um_summaries` — последними.
- Архив — отдельный SQLite-файл (`UM_ARCHIVE_PATH`), не таблица в основной БД.
- Физическое удаление — только из архива и только по сроку; «не сохранив — не удаляем».
- `mem_status`: размеры горячей/архива, дата прохода, что уедет следующим.
- Всё в стиле `mem_doctor`: авто-проход консервативный, ручной — dry-run/apply.

Механика «раз в неделю» (stdio — не демон): ленивый планировщик — при первом
вызове тула читаем `um_meta.retention_last_run`; если `now - last >= 7d` → проход,
метка. Гарантия «не чаще 7 дней», не «в 03:00». Cron-режима для (а) НЕТ:
`mem_doctor(mode=retention)` упоминался как желаемый, но не реализован — есть
только `mode=archive` (двигает oldest без учёта `retention_days`). Гэп заведён
в `docs/BACKLOG.md` (P3.5).

Открытый вопрос (математика): вектор ~1 КБ/сообщение (256 dim f32). Вариант (а)
держит вектор в горячей вечно → рост замедляется, но порог 1 ГБ НЕ гарантирован
(через ~1M сообщений вектора упрутся сами). Развилка: (а1) вектора в горячей
вечно, или (а2) при срабатывании порога вектор тоже уезжает в архив (горячий
recall старых перестаёт их находить, поиск по архиву — флагом/тулом).
Рекомендую (а2) как единственный способ честно держать порог.
